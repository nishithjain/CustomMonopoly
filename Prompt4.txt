Implement edition-configurable board layouts, card registries, card counts, and rent-level counts in the Customized Monopoly / Monopoly Ultimate Banking QR project.

## Decision

Board layout and card counts must not be globally fixed because the project supports customized editions.

UK and India should retain the physical Ultimate Banking configuration:

* 4 Player Cards
* 22 Property Cards
* 23 Event Cards
* 5 rent levels per property

Custom editions must be able to define different counts without changing Kotlin or validator source code.

Custom editions must also be able to define a different ordered board, including different space counts, space IDs, space types, Property placement, Event spaces/decks, Locations, Jail/GO placement, regions/sides, and relationships. JSON may select only typed space types and mechanics supported by Kotlin; it must never contain executable code, Kotlin class names, reflection targets, or arbitrary expressions.

## Scope and sequence

This is Prompt 4. Run it after dynamic edition selection and edition-aware artwork are complete. This task owns edition package structure, typed board layout, registry composition, structural counts, cross-file references, and structural runtime assumptions. It does not implement new Event action mechanics or general rule policies; Prompt 7 owns those behaviours.

Do not stop after analysis. Inspect the repository, implement the changes, update all affected tests, and run the relevant test suites.

## 1. Inspect the current implementation

Locate:

* UK and India `edition.json` files.
* Any board-space/order model, board images, position indexes, movement logic, and `board_layout.json` equivalent.
* `board_relationships.json` and all logic using board sides, neighbours, colour groups, or Location destinations.
* Edition configuration models and JSON parsing.
* The edition validator.
* Hard-coded constants for `4`, `22`, `23`, `49`, and `5`.
* Validation messages referring to fixed card counts.
* Card registry validation.
* Whether `card_registry.json` is global, common, or edition-specific, and whether it assumes UK Property/Event IDs.
* Property rent-level validation.
* Card generators or scripts using fixed loops or ranges.
* Runtime code that assumes exactly 22 Properties or 23 Events.
* Runtime code that assumes a fixed board order, fixed board-side partitions, or particular IDs at particular positions.
* Tests and fixtures built around the fixed counts.

Do not blindly replace every occurrence of these numbers. Determine whether each occurrence represents a card-count assumption or an unrelated gameplay value.

## 2. Extend edition.json

Add the following section to every edition’s `edition.json`:

```json
{
  "editionId": "uk",
  "name": "UK Edition",
  "cardConfiguration": {
    "playerCardCount": 4,
    "propertyCardCount": 22,
    "eventCardCount": 23,
    "rentLevelsPerProperty": 5
  }
}
```

Preserve all existing fields in `edition.json`.

Add the same configuration to India:

```json
"cardConfiguration": {
  "playerCardCount": 4,
  "propertyCardCount": 22,
  "eventCardCount": 23,
  "rentLevelsPerProperty": 5
}
```

Use the project’s exact naming and serialization conventions if a closely related configuration structure already exists.

Do not store:

```json
"totalCardCount": 49
```

The total is derived as:

```text
playerCardCount + propertyCardCount + eventCardCount
```

Storing both the individual counts and total would create two sources of truth.

## 3. Add edition configuration models

Add a model equivalent to:

```kotlin
data class CardConfiguration(
    val playerCardCount: Int,
    val propertyCardCount: Int,
    val eventCardCount: Int,
    val rentLevelsPerProperty: Int
)
```

Add it to the existing edition model:

```kotlin
data class EditionDefinition(
    // Existing fields
    val cardConfiguration: CardConfiguration
)
```

Use the actual existing edition model name.

The parsed configuration must be available to the validator and any generator that needs expected card counts. It is not the source of board order; ordered board spaces must come from `board_layout.json`.

Do not introduce a Kotlin map keyed by `uk`, `india`, or other edition IDs.

## 4. Validate the configuration itself

Validate the configuration before using it.

Requirements:

* Counts must not be negative.
* `playerCardCount` must be greater than zero.
* `propertyCardCount` must be greater than zero.
* `rentLevelsPerProperty` must be greater than zero.
* If the existing game model requires at least one Event Card, enforce that existing rule; otherwise allow zero Event Cards.
* Detect integer or parsing errors clearly.
* Report the edition ID and invalid field in validation errors.

Do not silently fall back to UK counts if the section is missing or invalid. Return a clear error such as:

```text
Edition 'custom-edition': cardConfiguration.propertyCardCount is missing or invalid.
```

Update all bundled editions and test fixtures so they include the required configuration.

## 5. Make validator counts edition-aware

Remove fixed validation equivalent to:

```kotlin
playerCards.size == 4
propertyCards.size == 22
eventCards.size == 23
allCards.size == 49
property.rentLevels.size == 5
```

Replace it conceptually with:

```kotlin
val config = edition.cardConfiguration

playerCards.size == config.playerCardCount
propertyCards.size == config.propertyCardCount
eventCards.size == config.eventCardCount

val expectedTotal =
    config.playerCardCount +
    config.propertyCardCount +
    config.eventCardCount

allCards.size == expectedTotal

property.rentLevels.size == config.rentLevelsPerProperty
```

Use the actual project types and APIs.

Validation errors must show expected and actual values, for example:

```text
Edition 'custom-edition': expected 24 Property Cards from edition.json, but found 22.
```

For rent levels, identify the affected property:

```text
Edition 'custom-edition', property 'PRP_07': expected 6 rent levels, but found 5.
```

## 6. Make the board layout edition-aware

Add an edition-owned `board_layout.json` if the project does not already have an equivalent authoritative file.

Use a typed schema equivalent to:

```json
{
  "spaces": [
    {
      "position": 0,
      "spaceId": "GO",
      "spaceType": "GO"
    },
    {
      "position": 1,
      "spaceId": "PROPERTY_CUSTOM_01_SPACE",
      "spaceType": "PROPERTY",
      "targetId": "PROPERTY_CUSTOM_01"
    },
    {
      "position": 2,
      "spaceId": "EVENT_MAIN_01_SPACE",
      "spaceType": "EVENT",
      "deckId": "main"
    }
  ]
}
```

This example is conceptual. Inspect existing engine concepts and use names that fit the codebase. Represent only supported typed space kinds such as GO, PROPERTY, EVENT, LOCATION, JAIL, or other types already implemented.

Requirements:

* Array order or an explicit contiguous `position` is the authoritative physical board order; do not maintain two independent orders.
* Positions must be unique, contiguous, and start at the documented base used by the engine.
* `spaceId` values must be non-blank and unique within the edition.
* Typed space payloads must be validated. For example, a PROPERTY space requires a valid edition Property reference, while an EVENT space may require a valid deck reference.
* Unknown space types must fail edition validation; they must not become no-ops or generic UK spaces.
* No Kotlin branch may select layout by checking `editionId`.
* Board size must be derived from the loaded space collection, not a UK constant.
* Movement, wraparound/GO detection, board-side/region targeting, neighbour lookup, and Location destinations must use loaded layout/relationship data where those concepts apply.
* The number of board EVENT spaces is independent from the number of Event Cards in an Event deck.
* The number of PROPERTY spaces must agree with the edition's intended Property placement. If the game supports off-board Properties, make that rule explicit rather than assuming equality.

Preserve clear source-of-truth boundaries:

```text
edition.json             edition metadata, definition version, and declared card/rent configuration
board_layout.json        ordered physical spaces and typed space references
board_relationships.json named sides/regions, neighbours, groups, and destinations derived from or referencing layout space IDs
properties.json          Property definitions and rent values
events.json              Event decks/cards and typed Event actions
card_registry.json       scannable edition-owned card identities and types
game_rules.json          supported behaviour modes and parameters
banking_values.json      monetary amounts
```

Do not duplicate board order in `board_relationships.json`. If existing data does so, choose one authoritative representation and migrate validation/consumers carefully.

## 7. Make the card registry edition-aware

A global registry cannot remain the authority for all Property and Event IDs when editions may use different IDs and counts.

Refactor toward one of these explicit designs:

* `data/common/card_registry.json` contains only genuinely reusable Player Cards, while each `data/editions/<editionId>/card_registry.json` contains that edition's Property/Event cards plus any edition-specific Player Cards and explicitly references the common Player Cards it uses; or
* Every edition has a complete resolved registry and explicitly imports/references common Player Cards through typed composition.

Do not copy common Player Card entries into multiple sources of truth without validation.

Runtime QR resolution for edition-owned cards must effectively use:

```text
active editionId + scanned card identity/type
```

Requirements:

* A Property/Event card valid only in another edition must not be accepted in the active edition.
* Identical card IDs in different editions are allowed when scoped by `editionId`.
* Arbitrary supported IDs must work; do not parse sequence numbers from `PRP_` or `EVT_` unless that syntax is explicitly part of the QR protocol.
* Registry entries must cross-reference the selected edition's Property/Event definitions and artwork manifest.
* Unknown, duplicate, wrong-type, and cross-edition scans must produce typed, useful failures.
* Common Player Cards must remain available during New Game without forcing selection of UK data.
* The resolved common-plus-edition Player Card set must match the selected edition's configured Player Card count.
* If editions can have different Player Card sets, New Game must select/load the edition before accepting Player Card scans; changing edition must clear incompatible registrations or require an explicit reset/lock flow.

## 8. Validate every relevant data source

Ensure configured counts are validated consistently against:

* Player Card definitions.
* Property definitions.
* Event definitions.
* `card_registry.json`.
* Edition-specific card-front manifests, if applicable.
* Edition-specific board layout and board relationships.
* Generated card outputs, if the generator validates output counts.

The total-card validation must be derived from the three configured counts.

Do not assume card IDs must end at `PRP_22` or `EVT_23`. Validate actual IDs, uniqueness, references, and counts according to the project’s existing rules.

Cross-file validation must also prove that:

* Every board Property reference resolves within the same edition.
* Every board Event deck/space reference resolves within the same edition.
* Every relationship/region/side references real layout spaces.
* Every edition-owned registry card resolves to exactly one matching definition.
* No UK definition is merged into a custom edition to make validation pass.

## 9. Remove fixed generator ranges

Inspect scripts and generators for code such as:

```python
range(1, 23)
range(1, 24)
```

or Kotlin equivalents that imply fixed card counts.

Where those ranges represent edition card discovery, replace them with:

* The actual cards loaded from edition data; or
* The edition’s `cardConfiguration`.

Prefer iterating over loaded card definitions rather than constructing IDs from expected counts.

Do not generate nonexistent card IDs simply because a configured count is larger.

The configured count is a validation expectation; actual card definitions remain the source of card content.

## 10. Audit runtime assumptions

Inspect runtime code for collection indexing, loops, UI labels, board-side handling, event selection, and card lookup that assume:

* 22 Properties
* 23 Events
* 4 available Player Cards
* 5 rent levels

Replace card-count assumptions with data-driven collection handling.

Rent-level operations must use the property’s actual rent-level list while the validator ensures it matches the edition configuration.

Do not change the existing minimum or maximum number of players merely because an edition contains more Player Cards. Available Player Cards and the gameplay player limit are separate concepts unless the existing rules explicitly connect them.

Do not change UK or India Event behaviour as part of this task. However, remove structural assumptions that an Event deck must contain exactly 23 cards, use `EVT_01–EVT_23`, or be attached to the UK board layout.

If other architectural limitations prevent additional Event Cards or Properties from working, identify and fix count-related limitations where safe, then report any remaining non-count limitation clearly.

## Acceptance criteria

The task is complete when:

1. UK and India continue validating with `4 / 22 / 23 / 5`.
2. The fixed total of `49` is no longer hard-coded and is derived from edition configuration.
3. Rent-level count is read from the edition configuration.
4. A custom edition with `5 / 24 / 20 / 6` validates successfully when its data matches.
5. Mismatched data fails with precise expected-versus-actual errors.
6. Validators and generators do not contain UK-specific count assumptions.
7. Adding an edition with different card counts requires data changes only.
8. Board size, order, space types, and relationships come from the active edition rather than UK constants.
9. Property/Event QR validation is scoped to the active edition.
10. A custom edition with a different layout and Event deck structure validates and runs without edition-specific Kotlin branches.
11. Existing UK and India gameplay and tests continue to pass.

After implementation, report:

* The final `edition.json` schema.

* Every hard-coded card-count assumption found and how it was handled.
* Every fixed board-layout/side/ID assumption found and how it was handled.
* Any remaining runtime limitation affecting variable card counts.
* Test commands executed and their results.
