Implement a repository-wide cleanup so every user-facing monetary value in the Customized Monopoly / Monopoly Ultimate Banking QR project uses the existing edition-aware `MoneyFormatter`.

## Problem

The game core already has a proper edition-aware `MoneyFormatter`, but parts of the Android UI still construct money strings using a hard-coded `M`.

Examples include:

```kotlin
"Paid: M${property.purchasePrice}"
"Balance: M$balanceAfter"
"New Rent: M$rentAfter"
```

This incorrectly displays `M` in India and future custom editions.

## Objective

All user-facing money output must go through the existing core `MoneyFormatter`.

Do not merely fix the three examples. Inspect the complete repository, implement the cleanup, add tests, and run all relevant test suites.

This project now treats editions as independent packages. A custom edition may use different board spaces, Property and Event IDs, Event definitions, banking scales, currency symbols, prefix/suffix placement, and numeric formatting. Money presentation must therefore depend only on the loaded edition's formatter, never on UK/India identity or a specific board/card structure.

## Scope and sequence

This is Prompt 3. Run it after edition selection is dynamic. It owns monetary presentation only. Do not change board structure, Event mechanics, balances, banking values, or gameplay arithmetic as part of this prompt.

## 1. Inspect the existing formatter

First locate and understand:

* The core `MoneyFormatter`.
* Its public API and configuration.
* How it obtains edition-specific formatting information.
* Existing correct usages of the formatter.
* How the active game’s `editionId` and edition data reach the Android UI.
* How New Game obtains its selected edition before a game starts.
* Any existing UI formatting helper or presentation mapper.

Reuse the existing formatter. Do not create a second Android-only currency formatter.

Do not add a Kotlin mapping such as:

```kotlin
when (editionId) {
    "uk" -> "M"
    "india" -> "₹"
}
```

Future editions must work without Kotlin changes.

Search all Kotlin source files, Compose screens, ViewModels, mappers, string resources, tests, and UI-message builders for hard-coded money formatting.

Distinguish monetary `M` usage from legitimate non-money uses such as identifiers, filenames, asset names, test names, or unrelated text. Do not blindly replace every letter `M`.

## 3. Replace manual formatting

Replace code such as:

```kotlin
"Paid: M$amount"
"Balance: M${state.balance}"
"New Rent: M$rent"
```

with the project’s actual formatter API, conceptually:

```kotlin
"Paid: ${moneyFormatter.format(amount)}"
"Balance: ${moneyFormatter.format(state.balance)}"
"New Rent: ${moneyFormatter.format(rent)}"
```

Use the exact existing `MoneyFormatter` API rather than inventing a parallel implementation.

Also replace formatting built with concatenation:

```kotlin
"M" + amount
```

and string-resource arguments where the currency marker is hard-coded:

```xml
<string name="balance">Balance: M%d</string>
```

String resources should accept an already formatted money string when appropriate:

```xml
<string name="balance">Balance: %1$s</string>
```

Do not put edition symbols into Android string resources.

## 4. Use the correct edition

For an active or resumed game, monetary values must be formatted using the formatter belonging to the game’s saved `editionId`.

The flow should effectively be:

```text
Active game editionId
→ loaded edition data
→ edition-aware MoneyFormatter
→ UI text
```

Do not use:

* A globally fixed UK formatter.
* The catalogue’s current default edition.
* The most recently selected New Game edition.
* A hard-coded UK fallback for a valid active game.

For the New Game screen, if any money values are shown before game creation, use the currently selected edition’s formatter.

When the New Game edition selection changes, any displayed monetary examples or values must update immediately.

## 5. Preserve numeric values for game logic

Keep monetary values as their existing numeric type for:

* Calculations
* Comparisons
* Debt settlement
* Rent transfer
* Auctions
* Persistence
* Game-engine commands

Only format values at the presentation boundary.

Do not parse formatted strings back into numbers.

Do not change gameplay arithmetic, rent values, balances, conversion rules, or banking values as part of this task.

If UI state needs both forms, retain the raw numeric value and expose a separately formatted display value.

## 6. UI messages and action results

Inspect messages generated in ViewModels, controllers, reducers, UI mappers, and composables.

Messages such as these must use the formatter:

If the core already returns a properly formatted message, display it directly instead of rebuilding it in the UI with `M`.

If the core returns structured numeric values, format them using the active edition before constructing the UI message.

Avoid storing newly generated user-facing messages with hard-coded currency text.

## 7. Compose architecture

Follow the project’s existing presentation architecture.

Do not instantiate or reload the edition formatter repeatedly during every recomposition.

Provide the formatter or formatted display values through the appropriate existing layer, such as:

* ViewModel/UI-state mapping
* A presentation mapper
* An existing game-session dependency
* A formatter function passed to a reusable composable

Use one consistent approach and avoid introducing global mutable state.

Ensure Compose previews use a fake or sample formatter rather than manually inserting `M`.

## 8. Tests

Add or update tests covering at least:

* UK output matches the UK formatter.
* India output matches the India formatter.
* A custom/test edition can provide different formatting without Kotlin UI changes.
* A custom/test edition with non-UK board-space, Property, and Event IDs still uses its formatter everywhere.
* Prefix, suffix, zero, negative, and any supported grouping/spacing behaviour come from the formatter rather than UI assumptions.
* `Paid` uses the formatter.
* `Balance` uses the formatter.
* `New Rent` uses the formatter.
* Purchase price uses the formatter.
* Rent and debt summaries use the formatter.
* Auction bids use the formatter.
* GO, Location, and Jail fees use the formatter.
* Resumed India games continue using the India formatter.
* Changing the New Game edition updates any displayed money formatting.
* Negative, zero, and positive values are passed correctly to the formatter.
* No double prefix is produced when a value is already formatted.

Use a fake formatter returning an unmistakable value such as:

```text
¤123
```

where useful. This proves the UI is calling the formatter rather than asserting only against another hard-coded currency symbol.

Update existing tests that expect literal strings such as `M200` so their expected values come from the configured formatter where appropriate.

## 9. Final source audit

After implementation, run a final repository search for hard-coded monetary `M` output.

Review every remaining result manually.

Any remaining `M` must be one of the following:

* Non-user-facing test fixture data.
* A legitimate card/game identifier.
* An asset filename.
* Documentation showing legacy behaviour.
* A formatter-owned UK currency configuration.

There must be no remaining Android UI code that manually prefixes a monetary amount with `M`.

## Acceptance criteria

The task is complete when:

1. Every user-facing monetary value goes through the existing `MoneyFormatter`.
2. UK games retain their expected UK formatting.
3. India games no longer incorrectly display a hard-coded `M`.
4. Custom editions can control money formatting without Android UI changes, regardless of their board layout, card IDs, or Event deck.
5. Active and resumed games use their saved edition’s formatter.
6. New Game uses the currently selected edition when displaying money.
7. Raw numeric values remain unchanged for calculations and persistence.
8. No duplicate UI-only currency formatter is introduced.
9. No user-facing `M${...}`, `"M" + amount`, or equivalent remains.
10. Existing and new tests pass.

After implementation, provide:

* A list of files changed.
* A list of hard-coded money-formatting locations fixed.
* Any remaining literal `M` occurrences and why each is valid.
* The formatter flow from active `editionId` to UI text.
* Test commands executed and their results.
