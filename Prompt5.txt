Implement edition-definition versioning in the Customized Monopoly / Monopoly Ultimate Banking QR project to prevent saved games from silently resuming with changed edition data.

## Problem

The app persists `editionId`, but it does not persist the version of the edition data used when the game started.

Example:

```text
Saved game:
editionId = india
definitionVersion = 1
PRP_01 purchase price = ₹6,000
```

If India’s JSON files are later changed, the saved game currently resumes with the new definitions. This could alter property prices, rent, debt, balances, board layout/order, space references, Event definitions/actions, or winner calculations during an existing game.

Treat `definitionVersion` as the version of the complete gameplay-affecting edition package, not only `edition.json`. It covers the edition's board layout, card registry, Property/Event definitions, banking values, board relationships, and game rules.

## Required policy

Use strict version compatibility:

```text
saved editionDefinitionVersion == installed definitionVersion
```

If the versions match, resume normally.

If they differ, reject Resume Game with a clear incompatibility message. Do not automatically load the newer definitions.

Because historical edition-definition files are not currently archived, do not attempt to migrate gameplay state between edition versions.

For existing unversioned saves, treat the current bundled UK and India definitions as version `1`, provided this change does not modify their gameplay data.

Do not stop after analysis. Inspect the repository, implement the change, add migrations and tests, and run the relevant test suites.

## 5. Check compatibility before resuming

During Resume Game:

1. Read the saved `editionId`.
2. Read the saved `editionDefinitionVersion`.
3. Load the currently installed definition for that `editionId`.
4. Compare its `definitionVersion` with the saved version.
5. Only construct or activate the game engine if the versions match.

Conceptually:

```kotlin
if (session.editionDefinitionVersion != edition.definitionVersion) {
    return ResumeGameResult.IncompatibleEditionVersion(
        editionId = session.editionId,
        savedVersion = session.editionDefinitionVersion,
        installedVersion = edition.definitionVersion
    )
}
```

Perform this check before recalculating rent, debt, balances, winner state, or other gameplay results using the installed definition.

Do not:

* Replace the saved version with the installed version.
* Update the database automatically.
* Resume with a warning.
* Fall back to UK.
* Delete or overwrite the incompatible save.
* Partially initialize the game before reporting failure.

A disabled catalogue entry should still be resumable when its saved and installed definition versions match. The catalogue `enabled` flag controls New Game availability, not saved-game compatibility.

## 6. Add a typed incompatibility error

Add a typed result/error following the project’s existing error-handling style.

It must carry:

```text

```

Avoid relying on parsing an exception-message string in the UI.

Show a clear message such as:

```text
Saved game cannot be resumed

This game uses India Edition data version 1, but version 2 is currently installed. Resuming it could change game values or rules.

The saved game has not been changed.
```

Provide a safe way to return to the previous screen.

Do not automatically delete the saved game. If an existing Delete Game action is available, keep it separate and preserve its existing confirmation flow.

## 7. Version bump rules

Add developer documentation explaining when to increment `definitionVersion`.

Increment it when changing edition data that can affect an existing game, including:

* Property purchase prices.
* Rent levels.
* Event behaviour or values.
* Banking values.
* Board-space count, order, type, IDs, targets, or deck references in `board_layout.json`.
* Board relationships, regions, sides, neighbours, or Location destinations.
* Card identities or references.
* Card counts or rent-level structure.
* Any rule-affecting edition configuration.

Changing an Event's display text alone does not require a version bump when it cannot change play. Changing its action type, action order, parameters, targets, value, deck membership, or follow-up requirements does require a bump.

A version bump is normally unnecessary for artwork-only changes, spelling corrections, or display-name changes that cannot affect gameplay. Do not confuse visual board artwork/layout with gameplay board-space layout: visual-only changes normally need no bump, while changes to `board_layout.json` do.

The process should be:

```text
1. Modify gameplay-affecting edition data.
2. Increment definitionVersion in that edition’s edition.json.
3. Run edition validation and saved-game compatibility tests.
```

## 8. Tests

Add or update tests covering:

### Edition loading

* UK loads with version `1`.
* India loads with version `1`.
* Missing version fails validation.
* Version `0` fails validation.
* Negative versions fail validation.
* A non-integer version fails parsing or validation clearly.

### New Game

* A new UK session stores `editionId = "uk"` and version `1`.
* A new India session stores `editionId = "india"` and version `1`.
* A custom test edition stores its configured version without Kotlin changes.
* A custom test edition with non-UK board-space, Property, and Event IDs stores its configured version without Kotlin changes.
* Autosave preserves both fields.

### Resume Game

* Saved version `1` plus installed version `1` resumes.
* Saved version `1` plus installed version `2` is rejected.
* Saved version `2` plus installed version `1` is also rejected.
* A mismatch returns the correct edition ID and both version numbers.
* The incompatible save remains unchanged.
* The game engine is not activated when versions differ.
* A disabled edition can resume when versions match.
* Missing edition data still produces the existing missing-edition error, distinct from version mismatch.

### Legacy migration

* An old saved game without a version migrates to version `1`.
* All balances, ownership, rent levels, undo state, jail state, and other saved fields remain unchanged.
* A migrated version-1 save resumes against installed version `1`.
* A migrated version-1 save is rejected against installed version `2`.

### Persistence

* Save and reload preserve `editionDefinitionVersion`.
* Entity/domain mappings preserve the value.
* JSON or Room round-trips preserve the value.
* Undo/session-copy operations do not lose or alter it.

The task is complete when:

1. Every bundled `edition.json` has `definitionVersion`.
2. New games save both `editionId` and `editionDefinitionVersion`.
3. Autosave and Resume Game preserve both values.
4. Resume succeeds only when saved and installed versions match.
5. Mismatched versions produce a clear typed incompatibility result.
6. Incompatible saves are not modified, deleted, or silently upgraded.
7. Existing unversioned saves migrate non-destructively to version `1`.
8. Disabled editions remain resumable when versions match.
9. No version is hard-coded per edition in Kotlin.
10. Gameplay-affecting board-layout and Event-definition changes are documented as version-bump triggers, while artwork-only changes are not.
11. Existing and new game-core, app, Room, persistence, and migration tests pass.
