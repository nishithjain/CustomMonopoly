Implement edition-aware card and board artwork for the Customized Monopoly / Monopoly Ultimate Banking QR Android project.

## Objective

The project currently has a global Android card-front manifest or lookup keyed only by `cardId`, and at least one generation or synchronization tool explicitly reads the UK edition. This is unsafe because different editions may reuse the same IDs with different artwork, or use completely different Property and Event IDs.

Make artwork discovery, synchronization, validation, and runtime lookup edition-aware.

The runtime identity for an edition-owned visual must be based on:

```text
editionId + cardType + cardId
```

Do not stop after analysis. Inspect the repository, implement the refactor, migrate existing UK and India assets, update tools and tests, and run all relevant validation and test suites.

## Scope and sequence

This is Prompt 2. Run it after Prompt 1 has made edition selection dynamic. This task owns artwork/manifests, asset tooling, and runtime visual resolution only. Do not implement board gameplay layout or Event mechanics here.

## Project direction

Treat each edition as an independent package. Editions may have different board layouts, card counts, card IDs, Event definitions, and artwork. Do not assume `PRP_01–PRP_22`, `EVT_01–EVT_23`, or UK filenames for future editions.

Common Player Card artwork may remain shared only when it is genuinely identical across editions. A custom edition may also own additional or replacement Player Card artwork. Property, Event, Player Card, and board artwork must never silently fall back to UK.

## 1. Inspect the current implementation

Locate and document:

* Every card-artwork asset directory.
* The global card-front manifest and its schema.
* Runtime image lookup APIs and all call sites.
* Card preview UI used by New Game, Active Game, Property, Event, debt, player details, and scan-result flows.
* Placeholder and missing-image behaviour.
* UK- or India-specific filenames and directory assumptions.
* Asset synchronization, manifest generation, card generation, and validation scripts.
* Hard-coded loops such as `PRP_01..PRP_22` and `EVT_01..EVT_23`.
* Any tool that directly opens `data/editions/uk/`.
* Gradle asset/source-set configuration.
* Tests for image resolution, manifests, and asset synchronization.

Use the existing asset-loading, Compose, dependency-injection, and scripting patterns. Do not add a second unrelated artwork system.

## 2. Establish the runtime asset layout

Refactor toward the following logical structure, adapting physical paths to the repository's existing asset pipeline:

```text
assets/cards/common/user/
assets/cards/editions/uk/property/
assets/cards/editions/uk/event/
assets/cards/editions/india/property/
assets/cards/editions/india/event/
assets/cards/editions/<editionId>/property/
assets/cards/editions/<editionId>/event/
assets/cards/editions/<editionId>/player/       # when not common
assets/boards/editions/<editionId>/
```

If the current project uses a `fronts/` directory, generated Android resource names, or another equivalent convention, preserve that convention while maintaining the same edition boundaries.

Requirements:

* Common artwork must contain only explicitly shared assets that an edition registry references deliberately.
* Edition-owned Property and Event artwork must live under that edition.
* Edition-specific Player Card artwork must live under that edition and override nothing implicitly.
* If board images or board-space visuals are packaged, they must also be edition-aware.
* Do not copy UK artwork into a custom edition as an implicit fallback.
* Do not infer an edition from a filename when the active or selected `editionId` is available.
* Preserve original image bytes, dimensions, and orientation unless an existing build step intentionally produces runtime derivatives.

## 3. Make manifests edition-aware

Replace the single global Property/Event mapping with either:

1. One manifest per edition; or
2. One generated manifest whose keys include the edition ID.

Prefer one manifest per edition when that fits the existing package structure.

A conceptual manifest entry is:

```json
{
  "editionId": "india",
  "cards": [
    {
      "cardId": "PRP_01",
      "cardType": "PROPERTY",
      "frontAsset": "cards/editions/india/property/PRP_01_Front.png"
    },
    {
      "cardId": "EVT_01",
      "cardType": "EVENT",
      "frontAsset": "cards/editions/india/event/EVT_01_Front.png"
    }
  ]
}
```

Use the repository's real filenames and serialization conventions rather than copying this literally.

The manifest must be generated or validated from the edition's actual `card_registry.json`, `properties.json`, and `events.json`. Do not manufacture IDs from numeric ranges.

Validate:

* Manifest `editionId` matches its directory/package.
* Card IDs are unique within their card type.
* Every edition-owned Player, Property, and Event card that requires a front has exactly one entry.
* Every manifest entry references a real packaged file.
* Every manifest card exists in the selected edition's registry and definition data.
* Card type agrees across registry, definition, and manifest.
* Extra stale entries and orphaned files are reported clearly.
* Validation errors contain `editionId`, `cardType`, `cardId`, and expected path where relevant.

Do not require identical IDs or counts across editions.

## 4. Refactor runtime lookup

Change the artwork resolver API from a shape equivalent to:

```kotlin
resolve(cardId)
```

to a typed edition-aware API equivalent to:

```kotlin
resolve(
    editionId = activeEditionId,
    cardType = cardType,
    cardId = cardId
)
```

Use the actual project types and naming conventions.

Requirements:

* Active Game uses the active session's saved `editionId`.
* Resume Game uses the saved edition after compatibility validation.
* New Game uses the currently selected edition for edition-owned previews.
* A common Player Card lookup is explicit from the selected edition's registry/composition; it is not achieved by falling back from a failed edition lookup.
* Property and Event lookups never use the catalogue default when another game edition is active.
* A missing asset returns the project's typed missing-artwork result or visible neutral placeholder with a useful diagnostic.
* A failed custom-edition lookup must not display a same-ID UK card.
* Do not store a mutable global current edition inside the resolver.

If card type is already encoded safely in a typed card reference, reuse it instead of adding redundant string parameters.

## 5. Update all UI call sites

Audit every place that displays card or board artwork.

Pass the correct edition identity through ViewModels, UI state, presentation mappers, and composables. Do not reload manifests on every recomposition.

Check at least:

* New Game player/card previews.
* Active Game scan results.
* Property purchase, auction, rent, and owner-landing flows.
* Event Card display and follow-up scan flows.
* Debt Payment property selection.
* Player details and owned-property lists.
* Undo/result/history displays that include artwork.
* Resume Game immediately after process restart.

Reusable composables should receive either a typed artwork reference or already resolved asset information, not infer UK internally.

## 6. Refactor generators and asset synchronization

Remove hard-coded UK/India iteration such as:

```python
for edition_id in ("uk", "india"):
```

and direct UK paths.

Discover editions from `data/editions/index.json` or, for maintenance tooling that must also validate disabled editions, from edition directories with explicit validation against the catalogue.

For each edition:

1. Load its edition metadata and card registry.
2. Load its actual Property and Event definitions.
3. Discover artwork from its configured directory.
4. Generate/copy the runtime manifest and derived assets.
5. Validate exact cross-references and report missing or extra assets.

Prefer iterating over loaded definitions instead of generating sequential IDs.

Add an explicit single-edition option such as `--edition <editionId>` if consistent with the existing script CLI, while retaining an all-editions mode for builds and CI.

Do not require Kotlin changes when a new supported edition and its artwork are added.

## 7. Build integration

Run asset synchronization and validation automatically before Android packaging, or wire the existing verification task into the appropriate Gradle pre-build/check lifecycle.

Requirements:

* The task must be deterministic and incremental where practical.
* A missing or invalid edition asset must fail the build with a precise message.
* It must not rewrite source artwork unnecessarily on every build.
* It must not include `local.properties`, build outputs, caches, or unrelated files.
* CI must execute the same validation used locally.

Use the project's current build conventions. Avoid fragile absolute paths.

## 8. Migration and compatibility

Migrate existing UK and India manifests/assets without changing their visible output.

If an old global manifest must temporarily remain for compatibility, production lookup must no longer use it for edition-owned Property or Event artwork. Remove it when all call sites and tests have migrated.

Artwork-only changes normally do not require an `editionDefinitionVersion` bump. However, changing a card ID, card type, registry membership, board-space reference, or gameplay definition does require the version policy from the versioning task.

## 9. Tests

Add or update tests covering at least:

* UK Property and Event artwork resolves from UK paths.
* India Property and Event artwork resolves from India paths.
* The same `cardId` in UK and India resolves to different edition assets.
* A custom edition with non-UK IDs resolves without a Kotlin constant.
* A custom edition may have different Property and Event counts.
* Missing artwork reports the exact edition, type, and card ID.
* A missing custom asset never falls back to UK.
* Common Player Card artwork resolves explicitly.
* An edition-specific Player Card resolves from its edition and is available during that edition's New Game flow.
* Manifest/registry type mismatches fail validation.
* Orphaned and duplicate manifest entries fail validation.
* Asset synchronization discovers a test-only edition dynamically.
* No generator or runtime test requires `PRP_22` or `EVT_23` to be the final ID.
* Active and resumed India/custom games keep their own artwork after process recreation.

Run the relevant script tests, edition validators, `:game-core` tests, `:app` unit tests, and any available Android resource/packaging test.

## Acceptance criteria

The task is complete when:

1. Property and Event artwork is organized or generated per edition.
2. Runtime artwork lookup uses edition identity plus typed card identity.
3. Common Player Card artwork is handled explicitly.
4. UK and India preserve their current visible artwork.
5. Identical card IDs in different editions resolve correctly.
6. Arbitrary supported card IDs and counts do not require Kotlin changes.
7. Missing custom artwork never displays UK artwork.
8. Generators and synchronization scripts no longer hard-code UK or India.
9. Asset validation runs automatically before packaging or in the standard verification lifecycle.
10. Existing and new tests pass.

After implementation, provide:

* The old and new artwork directory/manifest structures.
* Files created, moved, or modified.
* Every UK-specific generator or runtime assumption removed.
* The runtime flow from active `editionId` and card reference to displayed asset.
* Any intentionally common assets and why they are safe to share.
* Validation/build tasks added.
* Test commands executed and their results.
